# INVminer NOID GPU Miner v0.1.44

This release makes NOID status output miner-grade and easier to monitor. Pool,
solo and benchmark logs now automatically select `H/s`, `KH/s`, `MH/s`,
`GH/s`, `TH/s`, `PH/s` or `EH/s`, including aggregate, kernel and per-GPU
rates. Pool protocol accounting remains an unscaled numeric `H/s` value.

The CUDA mining modules, work allocation and pool protocol are unchanged from
v0.1.43. Both packages are multi-architecture Linux x86_64 binaries; choose by
host driver compatibility, not GPU model. No proprietary Rust/CUDA source is
included in the archives or this public repository.

> **Binary-only risk:** this release may be incompatible with a particular GPU,
> driver, OS or pool state. Source is not provided, so users cannot independently
> rebuild, audit or patch it and must decide whether to trust the binary and its
> published checksums.

## Recommended command

All visible GPUs, recommended:

```bash
./invminer-noid \
  --pool stratum+ssl://stratum.innovlab.cc:19601 \
  --worker YOUR_NOID_ADDRESS.RIG_NAME
```

One selected GPU:

```bash
./invminer-noid \
  --pool stratum+ssl://stratum.innovlab.cc:19601 \
  --worker YOUR_NOID_ADDRESS.RIG_NAME \
  --device 0
```

Do not provide threads, nonces-per-thread, or batch parameters. Qualified
models select reviewed defaults; other supported models perform a bounded
first-run auto-tune and save it locally.

Optional RTX 4090 profile:

```bash
./invminer-noid \
  --pool stratum+ssl://stratum.innovlab.cc:19601 \
  --worker YOUR_NOID_ADDRESS.RIG_NAME \
  --device 0 \
  --power-limit 450 \
  --locked-core-clock 2400
```

Default clocks remain the general recommendation. Hardware controls are
optional; a failed unsupported control warns and continues with verified
defaults. Locked-core and offset tuning should not be combined without a
card-specific qualification.

## GPU measurements and compatibility evidence

Hashrate is the miner's NOID work rate. The v0.1.44 exact-package rows were run
without miner clock or offset arguments. Average/peak power was not sampled in
the short v0.1.44 gate and is therefore reported as `N/A`, not inferred from an
older run. Historical rows are prior physical compatibility evidence, clearly
separated from this release's exact-package tests.

| RTX 4070 SUPER ×6 | `sm_89` | CUDA 12 / 535.171.04 | Historical v0.1.43 multi-GPU gate; v0.1.44 endpoint unavailable | `53.450 MH/s/GPU`; `320.701 MH/s` aggregate | `220 W/GPU` | `219.51 W/GPU` aggregate average; `220.55 W` peak individual | default clocks |

| RTX 4090 | `sm_89` | CUDA 13 / 580.173.02 | Exact packaged v0.1.44 benchmark | `112.340 MH/s` total; `112.359 MH/s` kernel | factory `450 W` | `N/A` | no miner hardware-control arguments |
| RTX 5090 | `sm_120` | CUDA 13 / 595.84 | Historical physical lane | `159.135 MH/s` | `575 W` | `549.04 / 564.70 W` | default clocks |

The RTX 4070 SUPER single-card figures are the six-card aggregate divided by
six; the peak is the highest individual card sample. All six cards used one
shared user-pool connection and disjoint search allocation. The v0.1.44 mining
modules are byte-identical to that reviewed lane, but the physical host was
offline during this release gate, so the row is not presented as a v0.1.44
rerun. CUDA 13 was not physically tested on RTX 4070 SUPER in this release.

4090 performance varies materially by host power behavior, firmware, driver
and virtualization. These `112–114 MH/s` results are evidence for the listed
host, not a universal card promise. Refer to v0.1.43 for the broader historical
`99–118 MH/s` cross-host range and its power-qualified measurements.

The exact CUDA 13 package also completed a live RTX 4090 pool gate at
`100.279 MH/s` total and `113.630 MH/s` kernel, with 51 accepted, zero rejected
and one pending response at shutdown. Its status line used the new SI formatter
and did not expose the user identity or developer-fee payout identity.

## Developer fee

The compiled developer fee is 5% of effective GPU mining time: 95 minutes of
user work followed by a 5-minute fee window. The payout destination is embedded
and is intentionally absent from public material and normal runtime logs. Fee
preparation failure does not stop user mining; raw user/fee share counts are not
expected to form a 95:5 ratio when sessions receive different difficulties.

## Reliability and validation

- CUDA 12 passed 50 NOID tests and CUDA 13 passed 51; both flavors passed
  formatting and clippy with warnings denied.
- Every physical gate passed CPU/GPU exact vectors and search-result self-tests
  before benchmark or pool work began.
- Two independent clean builds of each flavor produced identical binaries.
- A failed CUDA device is isolated and rebuilt with bounded backoff; exhausted
  all-device recovery exits cleanly for service-manager recovery.
- Pool reconnect uses bounded exponential backoff. Share health requires at
  least 20 consecutive resolved rejections or more than half of a full
  100-response window before reconnecting.
- Status is rate-limited. Per-share, per-job and per-work-slice production logs
  remain absent, and the developer-fee payout destination is never logged.
- Archive members, native modules, version, GLIBC ceiling, private paths,
  endpoint identity and forbidden runtime-log templates passed static gates.
- The original workload on the RTX 4090 gate host was restored after testing.

The CUDA 12 host package embeds the reviewed native `sm_120` module produced by
the CUDA 13 toolchain because CUDA 12 cannot assemble that instruction path. It
links no CUDA 13 runtime and remains the broad host-compatibility package.
